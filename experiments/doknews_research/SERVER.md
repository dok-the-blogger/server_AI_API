# Серверный пилот dok.news: main и задачи ChatGPT

Этот вариант переносит выполнение исследования и его состояние на `main`.
ChatGPT собирает актуальную фактуру и управляет запуском через три узких MCP
инструмента. Выключение компьютера владельца или окончание вызова инструмента
не прекращает серверное задание.

Код подготовлен для первого сравнительного прохода на `gpt-6.1-sol`.
Серверная установка, подключение ключа, реальный проход Sol и расписание —
отдельные этапы; наличие этих файлов не означает, что они уже выполнены.
Полный первый проход Astra завершился на компьютере владельца 12 ноября 2026 г.
Сравнение расходов Sol пока не измерено.

## Устройство

| Часть | Ответственность |
| --- | --- |
| ChatGPT / согласованная задача | Прочитать архив, радар и память доступными инструментами; сформировать snapshot с честным покрытием; выбрать один request_id; разобрать досье. |
| DOK Agents | `ai_research_start`, `ai_research_status`, `ai_research_result`: короткие авторизованные запросы к существующему ai-service. |
| ai-service | HTTP-контроль, проверка свежести и размера, долговечная очередь SQLite, запуск отдельного дочернего worker. |
| Worker | Собственное окружение OpenAI SDK, чтение приватного ключа, подготовка пакета, один POST создания исследования, наблюдение и восстановление по сохранённым ID. |
| Приватное состояние вне Git | Очередь, исследованные версии сигналов, snapshot, request/manifest/receipt и готовые досье. |

Веб-поиск выполняется внутри API-исследования. Worker не получает DOK MCP
инструменты ChatGPT автоматически. В этой версии нет автономного сборщика
радара/памяти на сервере: snapshot передаётся при start. Серверный cron без
подготовки snapshot пока не является поддержанным сценарием. Задача ChatGPT
может быть источником snapshot после отдельного подключения этих инструментов
к её выполнению; эта интеграция должна быть проверена реальным запуском задачи.

Публикация статей, редакционное принятие кандидата, review радара и запись памяти
не входят в полномочия worker. Токен dok.news, позволяющий публикацию, ему не нужен.
Новых публичных портов, доменов, Redis или отдельного MCP приложения нет.

## Контекст и экономия

Layout 2 сохраняет полный пакет правил `doknews-editor`. В начале контекста идут
стабильные инструкции, затем канонически упорядоченные архив и память. Время
снимка, UUID, рабочее окно, наблюдательные метаданные и новые сигналы идут после
стабильных частей. Семантические даты, версии, тексты и вложенный порядок данных
сохраняются; исходный snapshot восстанавливается без потери полей.

Изменение архива, памяти или правил закономерно меняет соответствующий префикс.
Стабильный порядок создаёт возможность повторного использования кэша, но не
гарантирует cache hit между запусками. Новые параметры TTL не отправляются:
доступный SDK и обслуживающий endpoint ещё не проверены для их совместного
использования.

Ledger сравнивает signal_id, версию и содержательные поля. Время повторного
чтения не превращает тот же материал в новый сигнал. Изменившийся текст с
повторно использованной версией тоже обнаруживается. По умолчанию один проход
берёт до трёх новых/изменённых сигналов, указывает остаток и фактическое покрытие.
Режим `new_signals` требует адресной проверки этих кандидатов вместо нового
полного обзора повестки.

Новостное окно заканчивается в фактический `research_as_of` подготовки запуска.
`captured_at` отдельно сообщает, когда получены переданные данные. При задержке
в очереди снимок проверяется повторно. Нельзя освежать старые данные заменой даты.

## Проверенная исходная среда main

Наблюдение 12 ноября 2026 г.: Ubuntu 24.04.4 LTS, Python 3.12.3; действующий
`ai-service.service` работает от `ai-service:ai-service`, checkout `/opt/ai-service`,
основной Python `/opt/ai-service/venv/bin/python`. Перед установкой состояние
нужно сверить через DOK Deploy. В репозитории может оставаться старый пример
`ai-api.service`; он не описывает установленный unit и не должен его заменять.

Новый worker использует отдельный venv `/opt/doknews-research/venv`.
Установка закреплённого SDK не изменяет зависимости действующего AI-сервиса.
Необходимый SDK — `openai==3.49.0`, требования находятся в
`requirements-pilot.txt`. Сам HTTP-контроллер не импортирует этот SDK.

## Подготовка установки

Это инструкция для администратора `main`, а не журнал выполненных действий.
Код обоих репозиториев сначала проходит обычный review и выпуск через существующий
DOK Deploy. Рабочую конфигурацию и приватные файлы держат вне checkout.

После установки согласованной версии кода подготовить окружение:

```bash
sudo install -d -o root -g root -m 0755 /opt/doknews-research
sudo /usr/bin/python3.12 -m venv /opt/doknews-research/venv
sudo /opt/doknews-research/venv/bin/python -I -m pip install --only-binary=:all: -r /opt/ai-service/experiments/doknews_research/requirements-pilot.txt
sudo install -d -o ai-service -g ai-service -m 0700 /var/lib/doknews-research
sudo install -d -o root -g ai-service -m 0750 /etc/doknews-research
sudo install -d -o root -g ai-service -m 0750 /etc/doknews-research/policy
sudo install -d -o root -g ai-service -m 0750 /etc/doknews-research/policy/references
sudo install -o root -g ai-service -m 0640 /opt/ai-service/experiments/doknews_research/server.example.json /etc/doknews-research/config.json
```

Последняя команда предназначена для первой установки. При обновлениях не
перезаписывать существующий config: сохранить его выбранные параметры.

### Политика

В `/etc/doknews-research/policy` устанавливается актуальный приватный пакет
навыка, без редакционного сокращения:

```text
SKILL.md
references/DOKNEWS_EDITORIAL_POLICY.md
references/DOKNEWS_EDITORIAL_CALIBRATION.md
references/DOKNEWS_EDITORIAL_MEMORY.md
references/DOKNEWS_AI_EDITORIAL_GUIDE.md
```

Файлы — UTF-8, обычные файлы без symlink, `root:ai-service`, права `0640`.
Полный пакет не коммитится в этот репозиторий. Manifest каждого исследования
сохраняет хеши фактически использованных инструкций. Изменение политики требует
установки обновлённого пакета до нового исследования.

### Ключ и конфигурация

Владелец устанавливает скачанный OpenAI key через защищённый административный
канал в `/etc/doknews-research/openai.key`, `root:ai-service`, права `0640`.
Допустим также файл владельца `ai-service` с правами `0600`.
Формат серверного credential — один ключ в UTF-8 файле; BOM и конечный перевод
строки допускаются. Расширение `.key` нормально; JSON-обёртка для этого серверного
пути не используется. Содержимое не передаётся через чат, аргументы команд,
Git, snapshot, конфигурационный JSON или журналы.

Ключ читает только процесс worker. При заданном `openai_key_file` этот файл
приоритетнее `OPENAI_API_KEY`. Альтернатива — заранее установленная переменная
окружения worker; для неё `openai_key_file` должен быть `null`. Пример конфигурации
использует файл, чтобы не добавлять ключ в окружение основного AI-процесса.

`AI_API_RESEARCH_API_TOKEN` — отдельный Bearer token для research HTTP. При его
отсутствии сохраняется совместимый fallback к `AI_API_API_TOKEN`. Для изолированной
настройки research не нужно менять авторизацию других маршрутов ai-service.
Согласованная копия у DOK Agents — `DOK_AGENTS_RESEARCH_API_TOKEN` (fallback к
`DOK_AGENTS_EMBEDDINGS_API_TOKEN`). Эти токены не заменяют ключ OpenAI; адрес берётся из существующего
`DOK_AGENTS_EMBEDDINGS_BASE_URL` (loopback, обычно `http://127.0.0.1:9000`).
Инструменты появляются при включённых `DOK_AGENTS_ENABLED` и
`DOK_AGENTS_EMBEDDINGS_ENABLED` после выпуска кода dok-agents и обновления
каталога инструментов в клиенте.

Пример `server.example.json` выключен: `api_enabled=false`. В конфигурации
заданы модель Sol, `medium`, до трёх сигналов, snapshot не старше часа и 900 секунд
наблюдения. Владелец уже разрешил сравнительный пилот без денежного лимита;
`spend_control` не отправляется. Время наблюдения и число сигналов ограничивают
работу, но не являются точным денежным потолком.

### Проверка перед включением

Под учётной записью сервиса выполнить отдельный offline check:

```bash
sudo -u ai-service /opt/doknews-research/venv/bin/python -I -X utf8 /opt/ai-service/experiments/doknews_research/server_runner.py check --config /etc/doknews-research/config.json
```

Он проверяет конфигурацию, доступность приватных файлов, версию SDK и комплект
политики, не создавая API-сессию и не исполняя очередь. Успех не доказывает
доступность модели, действительность ключа на стороне OpenAI или наличие кредитов.
`worker --once` для такой проверки не подходит: он может исполнить queued job.

В существующий runtime-файл `/opt/ai-service/.env` добавить путь и отдельный
служебный research token; установщик сохраняет остальные значения и права файла.
Форма записи пути:

```dotenv
AI_API_RESEARCH_CONFIG_PATH=/etc/doknews-research/config.json
```

Для ai-service не создаётся systemd drop-in: установленный Deploy-контракт
требует пустой `DropInPaths`. `ExecStart`, пользователь и unit сохраняются.
После согласованной установки runtime-конфигурации выполняется штатный restart.
С `api_enabled=false` подключены только чтения сохранённых
работ; новый платный worker не запускается. Без пути research вообще отключён.

Для первого живого прохода после успешного check установить `api_enabled=true`
и штатно перезапустить ai-service. Родитель запускает ровно один отдельный worker;
дополнительный cron или второй unit для того же state_dir не создаётся.
Приватный `worker-status.json` сообщает phase и observed_at. Новый start принимается
только при свежем heartbeat `idle`/`running` после проверки SDK, ключа и политики.
`/readyz.ai_research` у DOK Agents подтверждает только готовность локального
HTTP-клиента, не состояние worker или OpenAI.
Если дочерний процесс завершится, общий `/health` ai-service может оставаться
успешным. Устаревший heartbeat остановит новые исследования; автоматического
перезапуска дочернего процесса внутри ai-service нет. Для восстановления нужен
разбор причины и штатный рестарт сервиса.

## Первый запуск из ChatGPT

1. Прочитать актуальную редакционную политику и фактуру штатными read-инструментами.
   Snapshot сохраняет source IDs, версии, содержимое, `captured_at` и явное coverage
   архива, радара и памяти. Неполное чтение помечается как неполное.
2. Выбрать один canonical UUID `request_id`; consumer — `doknews-api-hourly`.
   Отправить через `ai_research_start` только request_id, consumer и snapshot.
3. Сохранить job_id. `queued` означает приём задания, а не окончание исследования.
   Проверять `ai_research_status` короткими вызовами; долгий HTTP-вызов не нужен.
4. При `completed` прочитать `ai_research_result`. Проверить ссылки, первоисточники,
   даты, ограничения, дубли и соответствие правилам до редакционного принятия.
5. Сопоставить receipt/manifest и Usage платформы за этот запуск. Неизвестный
   usage не считать нулём; session/root usage не суммировать. Новый профиль меняет
   модель и объём поиска, поэтому сравнение с первым Astra — проверка полезности
   и стоимости рабочего процесса, а не чистый benchmark одной замены модели.

Start ограничен 480 000 UTF-8 байтами сериализованного snapshot. Полный результат
ограничен 2 000 000 байтами и проверяется по SHA256. Лишние поля модели, адреса,
пути, ключа или arbitrary tool в запросе не разрешены.

При отсутствии новых версий возвращается `no_signals`, job_id=null и исходное
coverage. API-исследование не создаётся. Это относится только к переданному набору;
не доказывает отсутствия новостей за его пределами. Если новых сигналов больше
трёх, `pending_remaining` показывает оставшиеся. Следующий batch — отдельное
разрешённое исследование, а не скрытый автоматический цикл.

## Повторы, остановка и восстановление

Точный повтор request_id + consumer + неизменённый snapshot возвращает ту же
работу, даже после завершения, остановки worker или устаревания снимка. Изменение
payload при прежнем ID даёт конфликт. После сетевого таймаута start использовать
тот же ID и данные либо читать известный job_id. Новый UUID не решает неизвестный
исход и не должен использоваться для обхода защиты.

Claim очереди и запись receipt предшествуют платному POST; SDK retries выключены.
Сохранённая сессия после обрыва читается по известным session_id/turn_id без
повторного создания исследования. Отмена — отдельный запрос, а не доказанный
результат. Если срок прошёл и отмена не подтверждена, worker повторяет запрос отмены
не чаще одного раза в минуту и продолжает чтение состояния.

SIGTERM останавливает приём следующего задания. Родитель даёт worker завершить
обработку остановки; принудительное завершение процесса не доказывает отмену
удалённой сессии. На следующем старте сначала восстанавливаются незавершённые
задания, затем допускается новая работа.

`unknown`, `failed`, неидентифицированная сессия и ошибка подготовки блокируют
дальнейшие исследования до разбора. В пилоте намеренно нет автоматического
reset/abandon/requeue. Для круглосуточной эксплуатации понадобится отдельная
операторская процедура подтверждённого закрытия таких состояний. Не удалять
SQLite, receipt или каталоги runs для обхода блокировки.

Сигнал отмечается исследованным только при `phase=completed`,
`result_status=available`, совпадении run_id и проверенном досье. Это завершение
работы исследователя, не подтверждение каждого факта и не разрешение публикации.

## Хранение и эксплуатация

`/var/lib/doknews-research` содержит SQLite, `inputs/`, `runs/`, lock и heartbeat.
Каталоги состояния имеют права `0700`, приватные файлы — `0600`. Результаты
сохраняются независимо от checkout и переживают выпуск новой версии кода.
Backup SQLite требует согласованного снимка с WAL или штатного backup API;
копирование одного файла БД во время записи не является надёжным backup.

HTTP/MCP возвращают только разрешённые поля состояния и готовое досье. Ключ,
локальные пути, полный request и provider error не входят в публичный receipt.
MCP audit сохраняет технические метаданные, не snapshot/досье. Источники и результат
остаются недоверенными данными, даже если прошли проверку хеша.

Чтобы приостановить новые задания, выключить `api_enabled` и штатно перезапустить
сервис. Чтение уже сохранённых результатов доступно при сохранённой конфигурации
и авторизации. Незавершённые remote sessions перед длительным выключением
нужно проверить отдельно; выключенный worker не выполняет recovery/cancel.

Расписание, автоматическое принятие/публикация и перенос существующих задач
этой установкой не создаются. Первый этап завершается одним проверенным Sol-досье
и измерением расхода, после чего выбирается регулярный профиль работы.
